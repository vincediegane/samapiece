# Design -- #23 Worker d'envoi de notifications sur depot correspondant

## Approche

L'evenement declencheur est la creation d'une Piece (le statut DISPONIBLE est fixe une seule fois, dans le constructeur de Piece, jamais atteint par une transition ulterieure -- confirme par lecture de Piece.java/StatutPiece.java/PieceService.creer()). Le rapprochement alerte<->piece (y compris la verification du numero de document via NumeroDocumentHasher.verifier, qui necessite le numero en clair) est effectue de facon synchrone et en-process dans un @TransactionalEventListener(AFTER_COMMIT), exactement le meme pattern que PieceIndexationListener (Meilisearch) : PieceService.creer() publie un evenement Spring interne (jamais serialise, jamais expose au broker) qui porte le numero de document en clair le temps du calcul, puis ce dernier est immediatement abandonne. RabbitMQ n'est utilise que pour la partie fiable/asynchrone qui suit -- la tentative d'envoi SMS et son retry avec backoff -- une file dediee (alerte.correspondance.*) calquee sur la topologie deja en place pour sms.* (#21) : 3 etages TTL+DLX (30s/2m/10m) puis dead-letter, un message AMQP par (piece, alerte) trouvee. C'est un compromis assume : le critere d'acceptation #2 du ticket ("le consumer... retrouve les alertes correspondantes") est interprete comme decrivant le comportement observable du pipeline evenementiel dans son ensemble, pas litteralement le code execute dans la methode @RabbitListener -- voir Decisions cles paragraphe 1 et Points ouverts. Le prix de ce choix : zero exposition du numero de document en clair sur le broker (coherent avec les paragraphes 9.2/10.2/10.4 du cahier des charges) et zero faux-positif de rapprochement, contre une divergence de lecture du critere d'acceptation qui doit etre validee par le spec-writer/PO.

## Fichiers/modules impactes

Aucun fichier de ce perimetre n'existe encore (premier ticket touchant le rapprochement alerte<->piece). Tout est a creer, sauf les points listes en "fichiers modifies".

Backend -- nouveau, dans sn.samapiece.alertes (le module possede deja Alerte/AlerteRepository/AlerteContactChiffrementService, c'est le bounded context naturel pour porter la logique de rapprochement ; reutilise sn.samapiece.notifications.PasserelleSms comme seul point de sortie SMS, comme prevu par le javadoc de PasserelleSms qui mentionne explicitement "#23 (worker metier)") :

Pour chaque alerte retenue, publie un AlerteCorrespondanceMessage sur alerte.correspondance.exchange / routing key de consommation directe.
- AlerteCorrespondancePieceMatchingListener.java -- @Component, @TransactionalEventListener(phase = AFTER_COMMIT), ecoute PieceDisponibleEvent, delegue a AlerteCorrespondanceService.
- AlerteCorrespondanceMessage.java -- record (alerteId, pieceId, nombreTentatives) ; volontairement minimal, aucune donnee personnelle en clair (ni numero de document, ni contact). Sur le modele de SmsRetryMessage.
- AlerteCorrespondanceRabbitConfig.java -- topologie AMQP dediee (voir Decisions cles paragraphe 2) : exchange alerte.correspondance.exchange, files alerte.correspondance.retry.30s/2m/10m, alerte.correspondance.consume, alerte.correspondance.dead-letter -- copie quasi a l'identique de SmsRabbitConfig.
- AlerteCorrespondanceProperties.java -- @ConfigurationProperties(prefix = "samapiece.alerte-correspondance") : max-tentatives, retry-ttl-30s-ms/2m-ms/10m-ms -- copie de SmsProperties, non fusionnee avec elle (voir Decisions cles paragraphe 3).
- AlerteCorrespondanceRetryListener.java -- @RabbitListener(queues = alerte.correspondance.consume) : recharge Alerte par id (re-verifie active -- voir Risques), Piece par id (pour composer le texte du SMS avec des donnees fraiches -- numero de fiche, nom du poste), dechiffre le contact via AlerteContactChiffrementService, reconstruit un NumeroTelephone, appelle PasserelleSms.envoyer(...). En cas d'echec (a definir precisement avec le spec-writer -- voir Points ouverts, car PasserelleSms.envoyer() ne renvoie aujourd'hui aucun statut de succes/echec synchrone, contrairement a PasserelleSmsHttpClient.tenterEnvoiDirect() utilise en interne par SmsRetryListener), republie vers l'etage de backoff suivant puis, apres max-tentatives, vers alerte.correspondance.dead-letter -- meme algorithme que SmsRetryListener.routingKeyPourTentative.

Backend -- nouveau, dans sn.samapiece.enregistrement (proprietaire du cycle de vie de Piece) :
- PieceDisponibleEvent.java -- record (pieceId, typeDocument, nomTitulaire, prenomTitulaire, numeroDocumentClair, dateNaissanceTitulaire, numeroFiche, posteNom). Evenement Spring interne uniquement (jamais serialise sur le broker) -- porte le numero de document en clair car c'est le seul point du systeme ou cette valeur existe encore en memoire hors de la requete HTTP d'origine (Piece ne le persiste jamais, cf. paragraphe 9.2).

Backend -- fichiers modifies :
- PieceService.java -- creer() publie en plus un PieceDisponibleEvent juste apres le PieceIndexableEvent existant (meme emplacement, memes garanties AFTER_COMMIT).
- backend/src/main/java/sn/samapiece/alertes/AlerteRepository.java -- ajout de findByActiveTrueAndTypeDocumentAndNomTitulaireIgnoreCase(TypeDocument, String).
- backend/src/main/resources/db/migration/V8__index_alerte_correspondance.sql (nouveau -- V7 est la derniere version utilisee) : index partiel CREATE INDEX idx_alerte_correspondance ON alerte(type_document, nom_titulaire) WHERE active = true -- voir Risques (performance du rapprochement).

## Decisions cles

1. Rapprochement fait en-process (AFTER_COMMIT, meme thread que la requete de creation), pas dans le consumer AMQP. C'est la seule facon de faire beneficier le rapprochement du numero de document en clair (necessaire pour NumeroDocumentHasher.verifier -- meme mecanisme que RecherchePubliqueService, la seule autre partie du code qui resout deja ce probleme) sans jamais le faire transiter par le broker. Alternative rejetee : transmettre le numero en clair dans le message AMQP pour que le consumer fasse le rapprochement comme le suggere litteralement le libelle du critere d'acceptation -- rejetee car cela ferait persister (meme brievement, dans les files de retry durables) une donnee personnelle sensible sur un composant d'infrastructure, a l'encontre des paragraphes 9.2/10.2/10.4. Autre alternative rejetee : ignorer le critere numeroDocument dans le rapprochement (ne matcher que type+nom+prenom+date) pour permettre un vrai rapprochement cote consumer sans donnee sensible sur le fil -- rejetee ici mais documentee en Points ouverts, car elle degraderait la precision (davantage de faux-positifs pour les alertes n'ayant que numeroDocument comme discriminant).
2. File AMQP dediee alerte.correspondance.* plutot que reutilisation de sms.consume : le message ici porte un identifiant d'alerte/piece a rapprocher a nouveau au moment de la consommation (etat qui peut avoir change -- alerte desinscrite, piece retiree), pas un SMS deja pret a l'envoi. Reutiliser sms.consume aurait force SmsRetryListener a interpreter deux formats de message differents (SmsRetryMessage vs un format "a resoudre"), melangeant un retry technique de transport (deja resolu, #21) avec un retry metier (rapprochement + envoi, #23).
3. AlerteCorrespondanceProperties distinctes de SmsProperties (pas de mutualisation), pour permettre a l'exploitation de regler des backoffs differents entre le retry technique SMS et le retry metier de notification, meme si les valeurs par defaut sont identiques au depart -- prix : un peu de duplication de code (config + topologie), assumee comme le fait deja le repo (aucun exchange/queue partage n'existe entre modules a ce jour).
4. Mesure du delai <5 min en test : pas de sleep reel. Reduction des TTL de backoff a ~200ms via @DynamicPropertySource (comme SmsRetryIntegrationTest) et assertion Awaitility avec un timeout court (quelques secondes) sur la reception par FakePasserelleSms depuis l'instant de creer(). Cela valide que le chemin nominal (aucun echec, aucun passage par un etage de backoff) est de l'ordre de la seconde, ce qui demontre la marge par rapport a 5 minutes sans jamais attendre 5 minutes en CI. Le worst-case avec plusieurs echecs et passage par l'etage 10m depasse volontairement 5 minutes par construction (cf. AC "en cas d'echec... backoff... puis dead-letter") -- l'AC delai<5min porte explicitement sur les "conditions normales", pas sur le chemin d'echec.
5. Duplication de la logique de correspondance (variante de RecherchePubliqueService.correspond()) plutot qu'extraction d'un utilitaire partage entre recherche et alertes -- les deux comparent des types differents (Piece candidat vs requete publique, ici Alerte candidate vs evenement Piece), coherent avec le choix deja documente dans #22 (design #22, decision cle 8) de ne pas mutualiser tant qu'il n'y a pas un troisieme besoin.
6. PasserelleSms.envoyer() ne renvoie aucun statut synchrone de succes/echec (contrat volontairement fire-and-forget, cf. javadoc). AlerteCorrespondanceRetryListener ne peut donc pas savoir directement si son appel a "reussi" -- point a trancher avec le spec-writer (voir Points ouverts).

## Risques / points d'attention

- Performance du rapprochement : si le nombre d'alertes actives devient important, le filtrage additionnel (prenom/date/numeroDocument.verifier -- ce dernier fait un SHA-256 par alerte candidate) se fait en memoire sur la shortlist SQL (type_document, nom_titulaire ignoreCase). L'index partiel propose (V8) borne cette shortlist a un nom+type donnes, ce qui est acceptable au volume attendu (paragraphe 11.6, milliers a dizaines de milliers de fiches/an) mais deviendrait couteux si de nombreuses alertes partagent le meme nom tres courant -- a surveiller, pas bloquant pour ce ticket.
- Alerte desinscrite entre publication et consommation : le message AMQP ne porte que des identifiants (alerteId, pieceId). AlerteCorrespondanceRetryListener DOIT recharger l'Alerte depuis AlerteRepository et re-verifier isActive() avant tout dechiffrement/envoi (contactChiffre/contactIv sont nuls apres desinscription, cf. Alerte.desinscrire()) -- sans cette re-verification, une desinscription pendant les etages de backoff resterait sans effet sur une notification deja en file. A tester explicitement (cf. Fichiers/modules impactes -- Tests).
- Piece retiree/modifiee entre creation et consommation : le worker recharge aussi la Piece pour composer le SMS avec des donnees fraiches (numero de fiche, poste) -- si la Piece n'est plus DISPONIBLE au moment de l'envoi (retrait tres rapide), faut-il quand meme notifier (le depot a bien eu lieu) ou annuler l'envoi ? Non tranche ici, cf. Points ouverts.
- Absence de statut de succes/echec explicite sur PasserelleSms.envoyer() (Decision cle 6) : sans clarification, le worker ne peut pas implementer le retry/backoff de l'AC4 de facon fiable -- risque de bloquer le codeur si ce n'est pas resolu en amont dans la spec.
- Couplage avec #21 et #22 non merges : ce ticket depend de code present uniquement sur la pile de branches bolt/issue-21-passerelle-sms -> bolt/issue-22-alertes-recherche -> bolt/issue-23-worker-notification-depot. Le developpement doit rester base sur cette derniere jusqu'au merge sequentiel dans main.
- Minimisation des donnees personnelles : PieceDisponibleEvent porte le numero de document en clair, mais uniquement en memoire JVM, jamais serialise ni journalise (aucun log ne doit afficher event.numeroDocumentClair() -- a rappeler explicitement dans la spec/revue de code) ; sa duree de vie doit rester bornee au traitement synchrone du listener AFTER_COMMIT.
- Notification du citoyen deposant (accuse de reception, paragraphe 7.3) : le ticket #23 ne couvre que la notification du citoyen chercheur (alerte). La notification de l'agent deposant est mentionnee au paragraphe 7.3 mais absente des criteres d'acceptation de ce ticket -- a confirmer explicitement hors perimetre (voir ci-dessous) plutot que suppose.

## Hors perimetre

- Notification push et email (seul SMS existe dans l'infra, cf. #21/#22) -- deja documente comme hors perimetre par #22, s'applique aussi ici.
- Notification du citoyen deposant / accuse de reception (paragraphe 7.3) -- non demandee par les criteres d'acceptation de #23.
- Toute UI d'administration pour visualiser/rejouer manuellement la dead-letter alerte.correspondance.dead-letter -- non demandee, coherente avec l'absence d'UI equivalente pour sms.dead-letter.
- Renforcement du contrat PasserelleSms pour exposer un statut de succes/echec synchrone -- si necessaire, c'est un changement transverse a #21 qui deborde le perimetre de #23 (a confirmer avec le spec-writer, voir Points ouverts).
- Purge/retention des messages en dead-letter, alerting operationnel sur leur accumulation -- non traite ici.

## Points ouverts pour le spec-writer

1. Confirmer ou reformuler l'AC2 ("le consumer... retrouve les alertes correspondantes") a la lumiere de la Decision cle 1 : le rapprochement est fait avant publication (producteur), pas dans la methode @RabbitListener. Si un rapprochement effectue litteralement dans le consumer est requis, il faudra soit accepter la perte de precision sur le critere numeroDocument (Decision cle 1, alternative rejetee), soit accepter de faire transiter le numero en clair sur le broker -- les deux ont un cout different a trancher au niveau produit/CDP, pas uniquement technique.
2. Preciser le comportement attendu quand une Piece change de statut (retrait) entre sa creation et l'envoi effectif du SMS de correspondance (cf. Risques).
3. Trancher comment AlerteCorrespondanceRetryListener determine un "echec d'envoi" au sens de l'AC4, etant donne que PasserelleSms.envoyer() est fire-and-forget (Decision cle 6) -- options : etendre le contrat PasserelleSms (hors perimetre actuel, cf. ci-dessus) ou considerer que "l'echec" couvert par ce ticket est uniquement une exception levee synchronement par envoyer()/le dechiffrement/le rechargement JPA (NumeroTelephone.de() invalide, Alerte/Piece introuvable, etc.), et que l'echec de livraison SMS proprement dit reste entierement gere par le retry technique deja en place (#21, sms.retry.*), invisible ici.
4. Valeurs par defaut de samapiece.alerte-correspondance.max-tentatives / retry-ttl-* : proposees identiques a samapiece.sms (3 tentatives, 30s/2m/10m) faute d'exigence produit specifique -- a valider.
