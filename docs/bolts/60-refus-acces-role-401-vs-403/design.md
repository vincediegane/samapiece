# Design — #60 Refus d'accès par rôle renvoie 401 au lieu de 403

## Approche

Lecture du code actuel : `SecurityConfig` declare explicitement un AuthenticationEntryPoint (HttpStatusEntryPoint UNAUTHORIZED) mais aucun accessDeniedHandler, comme le decrit le ticket. En theorie ceci n'est pas le bug : quand exceptionHandling() ne fixe que l'authenticationEntryPoint, Spring Security conserve son AccessDeniedHandler par defaut (AccessDeniedHandlerImpl, reponse 403 a corps vide) pour toute AccessDeniedException/AuthorizationDeniedException dont l'Authentication courante n'est pas anonyme, et JwtAuthenticationFilter pose bien un UsernamePasswordAuthenticationToken authentifie (non anonyme) porteur du role (Role implements GrantedAuthority, prefixe ROLE_) avant tout @PreAuthorize.
 Verification empirique (lecture des tests, pas d'execution -- Docker/Testcontainers indisponible dans ce sandbox) : tous les controleurs @PreAuthorize sauf un endpoint ont deja un test d'integration @SpringBootTest + @AutoConfigureMockMvc (donc chaine de filtres reelle) qui pose un jeton valide de role insuffisant et attend status().isForbidden(), y compris l'exemple cite dans le ticket, POST /api/v1/pieces avec DEMO-ADMIN-001 (PieceIntegrationTest.creer_commeAdminNational_shouldRetourner403, deja sur main).
 Le comportement 403 semble donc deja correct et teste pour la quasi-totalite du perimetre ; le seul trou de couverture identifie est GET /api/v1/agents (AgentAdminController.lister()), l'autre exemple cite dans le ticket, qui n'a aucun test de role insuffisant.
 L'approche retenue est donc double : (1) fermer ce trou de couverture avec un test explicite, et (2) rendre le contrat 401/403 explicite et non tributaire d'un defaut implicite de Spring Security en declarant un accessDeniedHandler dedie dans SecurityConfig, symetrique a l'authenticationEntryPoint deja present -- cout quasi nul, comportement inchange (meme classe AccessDeniedHandlerImpl, meme corps vide), mais documente l'intention et protege contre une regression future si exceptionHandling() est retouche.
 Le codeur doit commencer par reproduire le bug a la main (curl contre un serveur lance localement, comme decrit dans le ticket) avant d'ecrire quoi que ce soit : si le 401 ne se reproduit plus sur l'etat actuel de main, documenter ce constat dans la PR (repond au critere d'acceptation "cause racine identifiee et documentee") plutot que d'inventer un correctif pour un bug qui ne se manifeste plus.

## Fichiers/modules impactés

- `backend/src/main/java/sn/samapiece/config/SecurityConfig.java` -- ajout d'un accessDeniedHandler explicite dans le bloc .exceptionHandling(...), a cote de l'authenticationEntryPoint existant (import org.springframework.security.web.access.AccessDeniedHandlerImpl).
- `backend/src/test/java/sn/samapiece/iam/AgentAdminIntegrationTest.java` -- ajout d'un test lister_avecRoleAgent_shouldRetourner403 (ou nom coherent avec les tests voisins creer_avecRoleAgent_shouldRetourner403 / desactiver_avecRoleAgent_shouldRetourner403 deja dans ce fichier), seul endpoint @PreAuthorize du depot actuellement sans test de role insuffisant.
- Aucun autre controleur protege par role (PieceController, PhotoController, AuditController, StatistiquesController) n'a besoin d'un nouveau test : chacun a deja au moins un test isForbidden() avec un jeton valide de role insuffisant (voir Decisions cles).
- Eventuellement un test cible et minimal au niveau SecurityConfig/filtre (nouveau fichier de test dedie, ou ajoute a un test existant) qui verifie directement la distinction 401 (jeton absent/invalide/expire) vs 403 (jeton valide, role insuffisant) sur un seul endpoint representatif, pour ancrer le contrat independamment de la logique metier de chaque controleur -- emplacement laisse au spec-writer.
- Aucun fichier frontend impacte (confirme par le ticket).

## Décisions clés

- accessDeniedHandler explicite plutot que reponse JSON personnalisee : utiliser new AccessDeniedHandlerImpl() tel quel (corps vide, comme le comportement actuel implicite et comme HttpStatusEntryPoint pour le 401) plutot qu'un handler qui ecrit un corps JSON structure. Ceci preserve l'existant (aucun test actuel n'attend de corps JSON sur un 403 de securite) et respecte le critere d'acceptation qui ne porte que sur le code de statut.
- Ne pas toucher a JwtAuthenticationFilter : son traitement d'un jeton absent/invalide/expire (ne pas authentifier, laisser anyRequest().authenticated() declencher l'AuthenticationEntryPoint) est deja correct et couvert par des tests (isUnauthorized() dans AgentAdminIntegrationTest). Le critere d'acceptation "jeton absent/invalide/expire continue de renvoyer 401" est une non-regression, pas un changement.
- Couverture de test par controleur, pas par methode : le critere d'acceptation demande "au moins un test par controleur protege par role" ; l'audit du code montre que ce critere est deja satisfait pour PieceController (6/6 endpoints testes), PhotoController (2/2), AuditController, StatistiquesController -- seul AgentAdminController.lister() manque. Ne pas dupliquer des tests deja presents sur les autres controleurs.
- Root cause documentee comme "defense en profondeur" plutot que "bug avere partout" : contrairement a l'hypothese du ticket, le code actuel ne semble pas systematiquement renvoyer 401 pour un role insuffisant -- les tests deja merges sur main (commit 6d0fc67, "Ajoute les tests d'integration RBAC du CRUD agents par role et par perimetre", entre autres) le contredisent pour la plupart des endpoints. Decision : traiter ce ticket comme un durcissement et une verification, pas une reecriture de la gestion d'exceptions Spring Security.

## Risques / points d'attention

- Contradiction a lever en premier : le repro curl du ticket (401 sur GET /api/v1/agents et POST /api/v1/pieces avec role insuffisant) ne correspond pas a ce que les tests MockMvc deja merges demontrent pour POST /api/v1/pieces (403 teste et presume vert en CI). Le codeur doit reproduire manuellement avant de conclure ; si le 401 est confirme sur GET /api/v1/agents specifiquement, creuser une difference GET vs POST (peu probable vu le mecanisme @PreAuthorize identique) ou une difference d'etat de compte (DEMO-AGENT-001 reellement actif, doitChangerMotDePasse) plutot qu'une difference de securite globale.
- ForcerChangementMotDePasseFilter s'execute pour toute requete authentifiee (sauf PUT /api/v1/agents/moi/mot-de-passe, GET /api/v1/agents/moi, POST /api/v1/auth/refresh, /actuator/*) et court-circuite vers une 403 (MotDePasseTemporaireNonChangeException) avant que @PreAuthorize ne s'evalue, si authentication.getDetails() vaut Boolean.TRUE (claim doitChangerMotDePasse). Si le compte DEMO-AGENT-001 du repro a ce flag actif, le repro curl pourrait confondre un 403 "mot de passe a changer" avec un 401 mal interprete par l'utilisateur -- a verifier mais hors perimetre de correction (comportement voulu, ticket #58).
- Ne pas casser le 401 existant : AuthExceptionHandler gere sn.samapiece.iam.AuthenticationException (exception metier, sans rapport avec org.springframework.security.core.AuthenticationException) pour les echecs de login -- ne pas confondre les deux hierarchies en modifiant SecurityConfig.
- Aucun @ControllerAdvice ne capte AccessDeniedException/AuthorizationDeniedException aujourd'hui (verifie par recherche exhaustive dans backend/src/main/java) -- donc l'ajout d'un accessDeniedHandler dans SecurityConfig est bien le seul point de controle pertinent, pas de risque de conflit avec un @ExceptionHandler existant.
- Tests d'integration : toute nouvelle methode de test creant des Piece doit vider piece_sequence avant suppression des Poste (contrainte FK, echoue seulement en CI) -- non applicable au test AgentAdminController.lister() a ajouter (pas de creation de Piece), mais a garder en tete si le spec-writer etend la couverture a PieceController ou PhotoController.

## Hors périmètre

- Reecriture de JwtAuthenticationFilter ou de la gestion des jetons absents/invalides/expires (deja correcte, doit rester inchangee).
- Ajout d'un corps JSON structure sur les reponses 401/403 de securite (hors perimetre du critere d'acceptation, qui ne porte que sur le code de statut).
- Toute modification du flux doitChangerMotDePasse / ForcerChangementMotDePasseFilter (ticket #58, deja merge et fonctionnel).
- Modification frontend (le ticket l'exclut explicitement).
- Ajout de tests de role insuffisant sur des endpoints deja couverts (PieceController, PhotoController, AuditController, StatistiquesController) -- uniquement combler le trou identifie sur AgentAdminController.lister().
